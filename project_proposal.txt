# DFMIS — MASTER PRODUCT, ARCHITECTURE & SAAS PROPOSAL

VERSION: 2.0
STATUS: MASTER PRODUCT SPECIFICATION
PRODUCT: DFMIS — Farm Management & Intelligence System
LONG-TERM MODEL: MULTI-TENANT SaaS
INITIAL VERTICAL: Dairy / Livestock
TARGET PROFESSIONAL PLAN: Approximately $200/month
CURRENT ENVIRONMENT: Initial farm / development customer
CURRENT IMPLEMENTATION: PHP + MySQL/MariaDB

============================================================
0. IMPORTANT — THIS DOCUMENT OVERRIDES THE ORIGINAL PROJECT SCOPE
============================================================

The original project proposal described a:

"Simplified Dairy Farm Management System for university
demonstration purposes."

That is no longer the long-term product vision.

The current project is being transformed into a:

PROFESSIONAL FARM MANAGEMENT & INTELLIGENCE PLATFORM

with a future:

MULTI-TENANT SAAS BUSINESS MODEL.

The original university requirements remain useful as the
foundation and demonstration scope, but they are no longer the
quality, architecture, or product ceiling.

The existing project is neither discarded nor rebuilt from scratch.
It is evolved, under the following method:

1. The current implementation is audited against this specification.
2. Working functionality is preserved.
3. Sound architectural decisions are preserved.
4. Architectural conflicts are identified explicitly.
5. Foundational problems are fixed before they become expensive.
6. Development proceeds incrementally.
7. Complexity is not added without a demonstrated need.
8. Future SaaS features are not built before they are needed.

The goal is:

PRODUCTION-QUALITY CORE TODAY
+
SAAS-READY ARCHITECTURE
+
MULTI-FARM FUTURE
+
MULTI-VERTICAL FUTURE
+
AI INTELLIGENCE

6. MULTI-TENANCY ARCHITECTURE
============================================================

Tenant isolation is a FIRST-CLASS SECURITY REQUIREMENT.

Tenant isolation is not postponed until all modules are built.

The minimum appropriate foundation is evaluated and implemented now.

Potential structure:

organizations
organization_users
farms
farm_users

with appropriate relationships.

A farm belongs to exactly one organization.

Users may eventually belong to one or more organizations and may
have different permissions across farms.

The exact implementation should be selected based on the current
codebase and future scalability requirements.

The design does not over-engineer.

Unnecessary abstractions are not created.

============================================================
7. TENANT CONTEXT
============================================================

A centralized and secure mechanism determines:

current user
current organization
current farm
allowed organizations
allowed farms
permissions

Tenant context must be determined server-side.

The following are never trusted:

- URL parameters
- hidden fields
- JavaScript
- client-supplied organization IDs
- client-supplied farm IDs

Every tenant-owned record must be accessed through authorized
tenant context.

============================================================
8. IDOR / CROSS-TENANT SECURITY
============================================================

A user must never be able to access another tenant's data by
changing:

?id=123

or POST data.

Example:

/modules/cows/view.php?id=123

must verify that cow 123 belongs to a farm the current user
is authorized to access.

The same applies to:

- cows
- health records
- milk records
- inventory
- medicine
- finance
- reports
- alerts
- documents
- uploaded files
- audit logs
- AI assessments

Test direct URL access and manipulated IDs.
